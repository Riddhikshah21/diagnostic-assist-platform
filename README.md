# Diagnostic Assist Platform

Diagnostic Assist helps service dispatchers understand reported machine problems, find similar historical cases and collect useful information before a technician visits.

The application runs locally. It combines multilingual hybrid retrieval with diagnostic drafts generated by a local language model. Suggested causes include references and quotes from historical cases.

**Status:** A working local application under active development. It is not yet production-ready.

This project builds on the [original Diagnostic Assist prototype](https://github.com/Riddhikshah21/diagnostic-assist).

## The problem

Service organisations have useful repair knowledge stored in free-text case descriptions, technician notes and resolutions.

These records may be multilingual, incomplete or contradictory. They do not contain a consistent symptom taxonomy or labelled root causes.

The goal is to help dispatchers collect better information and prepare technicians for the visit. Historical evidence supports that process; the technician still confirms the diagnosis onsite.

## How it works

1. The dispatcher selects an equipment type and enters the customer's description.
2. The application saves a session and retrieves similar historical cases.
3. The dispatcher reviews the original descriptions, technician findings, resolutions and replaced parts.
4. The dispatcher can request diagnostic suggestions.
5. The assistant assesses the request, then generates possible causes with supporting evidence.
6. The dispatcher records additional observations or answers, including `Unknown`.
7. Evidence is refreshed, and suggestions can be generated again.

Historical evidence remains visible while generation runs. If the model times out or returns an invalid response, the dispatcher can continue using the evidence.

A suggested follow-up question can be copied into the observation form. It is only saved after the dispatcher records the customer's answer. Questions can also be entered manually.

## Implemented features

- Historical-case validation and PostgreSQL storage.
- Repeatable case imports using organisation and case IDs.
- Stored multilingual embeddings with incremental updates.
- Equipment-type filtering.
- PostgreSQL keyword search and semantic search.
- Weighted Reciprocal Rank Fusion.
- Persistent sessions, observations and revision tracking.
- FastAPI backend and React interface.
- Local request assessment and diagnostic generation through Ollama.
- Validation of cited case IDs and exact source quotes.
- Evidence fallback when generation fails.
- Rejection of stale results when a session changes.
- Unit tests, optional database integration tests and evaluation scripts.

## Retrieval and generation

The database retrieval path searches customer descriptions using PostgreSQL full-text search and cosine similarity over stored embeddings.

The two result lists are combined using weighted Reciprocal Rank Fusion. Current defaults are:

- Keyword weight: `1.0`
- Semantic weight: `2.0`
- Candidate depth: `5` per search method
- Returned cases: up to `5`

These are development settings, not validated production settings.

Technician notes, resolutions and replaced parts are returned as evidence. They are not included in the current description search index.

The original in-memory CLI and evaluation baseline use BM25. PostgreSQL keyword ranking is a separate implementation and is not BM25. Equipment-family fallback exists in the original CLI, but is not implemented in the database API.

Generation uses two local model calls: request assessment and diagnostic drafting. A billing request should return no diagnostic causes, while an unclear request should ask for symptoms.

Cause explanations are assembled from cited quotes. Citation checks verify that the case and quote exist; they do not prove that the model interpreted the evidence correctly.

## Local setup

The commands below assume macOS or Linux.

### Prerequisites

- Python 3.11 or newer
- Node.js 22.12 or newer and npm
- Docker with Docker Compose
- Ollama
- Git

Local generation needs memory beyond the downloaded model size. Performance depends on hardware and other running applications.

### 1. Clone and install the backend

```bash
git clone https://github.com/Riddhikshah21/diagnostic-assist-platform.git
cd diagnostic-assist-platform

python3 -m venv .venv
source .venv/bin/activate

python -m pip install --upgrade pip
python -m pip install -e ".[dev]"
```

Run Python, migration and Docker commands from this project root.

### 2. Configure the application

Create `.env` in the project root:

```env
POSTGRES_DB=diagnostic_assist
POSTGRES_USER=diagnostic
POSTGRES_PASSWORD=local_dev_password
POSTGRES_HOST=localhost
POSTGRES_PORT=5433
APP_ORGANISATION_ID=local
OLLAMA_MODEL=qwen2.5:7b
```

These credentials are for local development. Do not commit `.env`.

### 3. Start PostgreSQL and apply migrations

```bash
docker compose up -d db
docker compose ps
```

Wait until the database is healthy, then run:

```bash
python -m alembic upgrade head
```

### 4. Import cases and generate embeddings

The repository includes fictional cases for development:

```bash
python scripts/import_cases.py \
  --data tests/fixtures/synthetic_cases.json \
  --organisation-id local

python scripts/embed_cases.py \
  --organisation-id local
```

The first embedding run downloads the multilingual model.

You can also place the original assignment sample at `data/sample_cases.json` and import that file instead. It is not included in the repository.

Imports update existing records rather than duplicating them. Changed descriptions invalidate their embeddings. Run the embedding command after importing updates; unchanged current embeddings are skipped.

### 5. Prepare the local language model

With Ollama running:

```bash
ollama pull qwen2.5:7b
ollama list
```

The API connects to Ollama at `http://127.0.0.1:11434`.

### 6. Start the backend

```bash
python -m uvicorn diagnostic_assist.api:app \
  --host 127.0.0.1 \
  --port 8000
```

The backend loads the embedding model during startup.

API documentation:

```text
http://127.0.0.1:8000/docs
```

Run one backend process for the current local setup. Diagnostic generation is limited to one concurrent request in that process.

### 7. Start the frontend

Open another terminal:

```bash
cd diagnostic-assist-platform/frontend
npm ci
npm run dev
```

Open:

```text
http://127.0.0.1:5173
```

The Vite development server forwards `/api` requests to the backend.

For the included fictional cases, select `COMP-100` and try:

```text
The machine will not start and the control panel has no lights.
```

If you imported the assignment sample, you can use `CX-450`.

## API endpoints

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/health` | Check database connectivity |
| POST | `/search` | Retrieve historical cases |
| POST | `/sessions` | Create a session |
| GET | `/sessions/{session_id}` | Load a saved session |
| POST | `/sessions/{session_id}/observations` | Save an answer or observation |
| GET | `/sessions/{session_id}/evidence` | Retrieve evidence using collected information |
| POST | `/sessions/{session_id}/diagnosis` | Generate a draft or return the evidence fallback |

The organisation is configured by the backend. Authentication is not implemented, so the current application should remain bound to localhost.

## Evaluation

Run the retrieval baseline from the project root:

```bash
python scripts/evaluate.py \
  --output evaluation/results/baseline.json
```

This uses the real multilingual embedding model with the included fictional cases and relevance judgments. It evaluates the in-memory baseline, not the PostgreSQL search implementation.

Diagnostic evaluation requires Ollama and the original assignment sample:

```bash
python scripts/evaluate_diagnosis.py \
  --data data/sample_cases.json \
  --query-id D-001 \
  --model qwen2.5:7b \
  --output evaluation/results/diagnosis-D001.json
```

Use `D-002` to evaluate the billing-request scenario.

The diagnostic runner uses a fixed candidate list to test generation separately from retrieval. It checks citation validity and citations to manually judged irrelevant cases. Cause interpretation, completeness and follow-up quality still require manual review.

These small development examples do not establish diagnostic accuracy or production performance.

## Probabilities

The application does not currently provide calibrated root-cause probabilities.

RRF scores, cosine similarity and model-generated confidence are not diagnostic probabilities. Reliable estimates would require a defined prediction target, reviewed outcomes and calibration on held-out data.

## Current limitations and next steps

- Retrieval can return irrelevant cases.
- Diagnostic causes can still misinterpret valid evidence.
- Automatic follow-up selection is not yet reliable.
- Generation can time out or reach its output limit.
- Overlength follow-ups can cause a draft to be rejected; malformed questions within the length limit are omitted.
- Long descriptions and growing conversation context need explicit token-budget handling.
- Generated drafts are not persisted and must be regenerated after reopening a session.
- Technician handoff, session completion and confirmed-outcome recording are not implemented.
- Authentication, operational monitoring and backup recovery still need implementation.
- The three-second first-output target and performance with 100,000 cases have not been verified.
- Daily imports and embedding updates are manual commands; scheduling is not implemented.

The next product step is a technician handoff built from the collected information and reviewed evidence. Further work will focus on evaluation, latency, larger datasets and operational reliability.
